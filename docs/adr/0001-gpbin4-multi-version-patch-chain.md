# ADR-0001：GPBIN4 多版本补丁链与可替换差异后端

- 状态：已接受（Accepted）；2026-10-01 修订：移除 chain 后端，仅保留 chunk 后端
- 日期：2026-10-01
- 决策范围：补丁制品形态、版本识别语义、差异存储后端契约
- 相关文件：`patcher/model.go`、`patcher/format.go`、`patcher/chain.go`、`patcher/chunk.go`、`patcher/build.go`、`patcher/apply.go`

## 背景（Context）

原程序只支持"一份补丁 = 一个源版本 → 一个目标版本"。要修复多轮 bug 时，玩家必须依次打上
`fix1`(A→B)、`fix2`(B→C)，无法一步到位。

需求明确为：

1. 补丁应当**包含 A→B 的差异 + B→C 的差异**，而不是直接计算 A→C 的单段差异；
2. 生成时保持原有逻辑，仅新增"附加旧版本补丁"这一步；
3. 新补丁的版本号自动递增；
4. 应用时自动识别玩家当前版本，并从该版本起升级到最新版本。

同时，用户授权进行完全重构，并要求方案具备长期可演进性（原先提到的
"内容寻址块存储"应可在不改动 CLI/载体/应用器的前提下接入）。

## 决策（Decision）

### 1. 制品从 GPBIN3 升级为 GPBIN4（链式）

补丁由**有序的版本段**组成，第 i 段表示"版本 i → 版本 i+1"。每一段沿用原有的
`Entry`/`DeltaOp` 模型（`add`/`update`/`delete` + `COPY`/`LITERAL`）。

- `patchVersion` 自动递增：无 `-prev` 为 1，否则为前缀版本号 +1。
- 单版本用法退化为只有 1 段的链，行为与旧版一致。
- 硬升级：不再读取 GPBIN3 制品（已发布的旧 EXE 自带旧代码，不受影响）。

### 2. 版本识别 = 内容指纹匹配，不引入版本标记文件

链由各段的 `oldHash/newHash` 回放推导出每个版本的 `VersionRef`（补丁触及路径的
存在性 + 大小 + BLAKE3）。应用时**从最早的版本开始逐个匹配，取第一个成功的版本为起点**。

- 匹配到最后一个版本 ⇒ 已是最新，直接退出且不落盘。
- 全部不匹配 ⇒ 列出每个候选版本的首个失败原因并中止，不修改任何文件。
- **面向用户的版本显示一律为链内序号 `v1`/`v2`/`v3`**。制品中的 `Label`（构建时的源目录名）
  仅作为溯源信息保留，不参与显示：目录名可能很长或带路径信息，序号才是稳定的版本标识。

不采用"在游戏目录放版本清单文件"的方案：那会引入可被篡改、且修改目录即失效的
额外持久状态。

### 3. 分离"稳定契约"与"可替换差异后端"

```
Release{PatchVersion, Payload}
Payload 接口: Kind / Sources / Target / StagesFrom / Encode
Stage{SourceIndex, Entries, Pool}
```

应用器只认识 `[]Stage`，因此更换差异后端不影响 CLI、EXE 载体、版本检测、
备份与回滚。

### 4. 唯一差异后端：chunk

| 项目 | 取值 |
|---|---|
| `payloadKind` | 2 |
| 字面量存放 | 去重的共享块池（`OpPoolRef`） |
| 跨文件复用 | 复用**本段被删除文件**的块（`OpCopyFrom`） |

块索引成本受控：只对"本段被删除的文件"建索引，不做全树分块扫描。

> **修订（2026-10-01）**：此前还存在 `payloadKind=1` 的 `chain`（内联差异）后端。由于两者
> 的使用体验、CLI 契约、检测与回滚路径完全相同，而 chunk 在"重命名/移动"与"跨段重复内容"
> 场景严格更优，按 **delete-first** 原则完全移除了 chain 后端。
> `payloadKind=1` 的旧制品会被明确拒绝并提示重新生成；已发布的旧升级工具自带旧代码，不受影响。

### 5. 同段内执行顺序：先 add/update，后 delete

`chunk` 后端的跨文件复制源取自"本段被删除的文件"，因此必须保证这些文件在读取
阶段仍然存在且内容未被修改。据此规定同段内先执行新增/修改、最后执行删除。

## 后果（Consequences）

**正面**

- 玩家在链上任意已知版本都能一步升到最新版本；已是最新时可安全跳过。
- 回滚复用既有 `restore.json` 契约，且改为逐段持久化，进程中断后仍可用 restorer 恢复。
- 新增后端不需要改动 CLI/载体/检测/回滚，方案具备可演进性。
- 制品为流式编解码，不再需要把整份补丁驻留内存。

**负面 / 代价**

- 补丁体积与生成耗时随链长线性增长（用户已接受）。
- 版本识别指纹只覆盖"补丁触及路径的并集"，不是全目录指纹。
- 单一后端，无分叉维护成本；`Payload` 契约保留，作为线格式判别与未来的扩展点。
- chunk 的收益具有场景性（重命名/移动、跨段重复内容）；线性改动场景与"内联差异"基本持平。
- chunk 的代价按**删除字节量**支付：为"本段被删除的文件"建块索引，即使内容最终未被复用。

## 备选方案与被否原因

1. **直接计算 A→C 单段差异**：被用户明确否决（要求保留 A→B 与 B→C 的差异）。
2. **应用端读取版本标记文件**：引入额外持久状态，易失效、易被篡改，弱于内容哈希。
3. **完整内容寻址（CAS）+ 全量清单重建**：需要重写应用模型（按 manifest 重建），
   且需为每个版本保存全量块清单；当前收益不足以支撑该复杂度，留作后续演进方向。
4. **在 GPBIN3 尾部并列多个 blob**：格式不自描述、无法携带版本标签，且尾部解析复杂。

## 兼容性边界

- 硬升级为 GPBIN4；新 CLI 无法把 GPBIN3 旧补丁作为 `-prev` 读取。
- `restore.json` 与 restorer 契约不变。
- 已移除的 `chain`（`payloadKind=1`）制品会被明确拒绝，并提示用当前版本 CLI 重新生成。
- Windows 上运行中的升级工具不能作为目标文件本身被替换。

## 后续演进

- 若需"任意版本互跳/降级"或更强的跨文件复用，可在同一 `Payload` 契约下新增
  内容寻址后端（`payloadKind=3`），无需改动 CLI、EXE 载体与回滚链路。
